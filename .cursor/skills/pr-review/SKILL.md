# PRレビュー

コードの変更、コミット、マージはしない。レビュー結果は日本語でPRにコメントする。

## 手順（写して使う）
```
- [ ] 1. IssueとPR本文から要件を読み取った
- [ ] 2. CIの結果（型チェック・ビルド）を確認した
- [ ] 3. 要件・テスト・設計の3観点で差分を見た
- [ ] 4. 出力ルールに沿ってPRにコメントした
```

## CIの扱い

型チェックとビルドはCI（GitHub Actions）で確かめている。エージェントはやり直さず、PRのCI結果を見るだけにする。失敗していれば、その内容を指摘に含める。

## 観点1 要件

IssueとPR本文の要件を満たしているか。

## 観点2 テスト

テストが要件を確かめているか。テストが通るかはCIの結果で判断する。

## 観点3 設計

指摘は最大3件。次を見る。

- 責務の混在
- 明らかな重複。同じロジックが3か所以上あるもの
- 公開APIの命名が既存の規約と合っているか
- 依存の向きの逆転
- TODOや一時的なコードの残置

## 出力ルール

- 指摘ごとに重大度 High / Medium / Low、根拠の行番号、修正案のコードを付ける。
- 変更前からある問題は「既存」と区別する。
- 確信がない指摘は書かない。
- 意図的かもしれない設計は質問の形にする。
- 最後は「問題なし」か「要修正（理由）」で締める。
